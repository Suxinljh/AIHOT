# WeChatHot 产品需求文档（PRD）

> **版本**：V1.1（产品方向已确认）
> **更新日期**：2026-10-21
> **产品类型**：面向微信公众号科技内容创作者的单用户 AI 内容工作台
> **基础项目**：[AIHOT](https://github.com/KKKKhazix/AIHOT) / 当前 `Suxin-新数字艺术` Fork
> **核心链路**：热点发现 → 选题决策 → AI 文章撰写 → 轻量排版 → 复制发布

---

## 0. 本版已确认的决策

V1.1 在 V1.0 草案基础上确认了以下方向，后续开发以此为准：

| 编号 | 决策 | 对产品的影响 |
|---|---|---|
| D1 | **完全单用户** | 不做注册、登录、团队、权限、协作；管理员登录即产品使用者，所有关注、已读、选题、稿件都是同一份数据 |
| D2 | **公开站逐步退场** | `/studio` 成为产品主界面，最终替代 AIHOT 的公开阅读界面；公开阅读页逐步下线，机器出口是否保留另行决定 |
| D3 | **行业分类固定为 7 类** | AI 大模型、汽车、数码硬件、软件与互联网、具身智能、电影与剧集、游戏；不再保留独立的“行业”分类 |
| D4 | **复用 AIHOT 已有的主题页能力** | 品牌库、品牌详情和主体识别参考现有 `/topics`、`industry/topics.json`、`ENTITIES`、`PUBLISHER_DOMAINS` 和品牌标记组件 |
| D5 | **保留公众号与 X 采集能力** | 继续使用现有 `mp_account`（极致了/Dajiala）和 `x_search`（SocialData），不重写适配器 |
| D6 | **Markdown 源码模式放到 P1** | V1 先做富文本编辑和纯文本/Markdown 导出 |
| D7 | **正文编辑器使用 TipTap** | 接受新增前端依赖，正文以受限文档 JSON 存储 |
| D8 | **发布日历放到 P1** | V1 不进入核心闭环 |

## 1. 产品概述

### 1.1 产品定位

WeChatHot 是一个面向微信公众号科技类内容创作者的**单用户内容工作台**。它把多渠道信息订阅、热点事件聚合、AI 选题评分、分阶段文章写作和微信公众号轻量排版放在同一个界面里，减少从信息发现到成稿发布之间的工具切换。

产品不是通用资讯阅读器，也不以自动化批量发文为目标。V1 聚焦两件事：

1. **发现值得写的内容**：把分散的信源变成可筛选、可解释、可跟踪的事件。
2. **提高单篇文章从资料到排版的处理效率**：从事件直接进入选题、写作、审核和复制。

V1 起，产品的主界面是 `/studio`，不再是 AIHOT 的公开资讯首页。公开阅读界面会随着功能迁移逐步退场，最终由工作台页面替代。

### 1.2 核心问题

| 问题 | 现状 | WeChatHot 的解决方向 |
|---|---|---|
| 信源分散 | 需分别查看官网、公众号、X、微博、GitHub 和科技媒体 | 统一信源入口与采集状态管理 |
| 重复信息多 | 多家媒体报道同一事件，反复浏览 | 以事件为单位聚合报道并展示时间线 |
| 热点难筛选 | 新闻热度不等于值得写 | 新闻价值、热度和选题价值分开显示 |
| 选题到写稿割裂 | 资料、角度、大纲、正文分散在不同工具 | 由事件一键进入选题和 AI 写作流程 |
| 微信排版耗时 | 正文写完后还需重复调整基础格式 | 在同一编辑器完成轻量排版并复制富文本 |
| 公开站与工作台混在一起 | AIHOT 的阅读界面不服务于创作 | 公开站逐步退场，工作台成为主界面 |

### 1.3 目标用户

- **唯一用户**：站点运营者本人。V1 不区分多用户，不做账号体系。
- **使用场景**：每天打开工作台，查看关注品牌和行业的新事件，判断哪些值得写，创建选题，生成并修改稿件，排版后复制到公众号后台手动发布。
- **不服务的对象**：普通资讯读者、团队协作成员、对外投稿作者。

### 1.4 设计原则

1. **单用户优先**：所有功能默认只有一个使用者；不为“以后可能多用户”提前加权限、组织和协作抽象。
2. **工作台优先**：`/studio` 是产品入口；公开阅读界面只作为过渡和内部能力保留。
3. **事件优先**：展示“发生了什么”，保留全部来源，不让重复报道占满列表。
4. **品牌可关注，渠道可控制**：关注品牌后可以选择其具体官网、社交账号、代码仓库和媒体报道范围。
5. **评分可解释**：同时提供新闻价值、热度和选题价值，并给出推荐理由、证据来源和缺失信息。
6. **写作由用户决策**：AI 提供角度、大纲、标题和草稿；事实核验和发布决定由用户完成。
7. **排版足够轻**：只解决字体、字号、行距、加粗、段落和基础图片，不构建复杂设计编辑器。
8. **采集能力可替换**：平台限制、收费和失效不应影响整个工作台；不可用的渠道要如实显示。

## 2. 产品范围与信息模型

### 2.1 V1 核心闭环

```text
关注行业 / 品牌 / 渠道
          ↓
定时采集与增量更新（官网、X、微信公众号、微博、GitHub、RSS、媒体）
          ↓
标准化 → 去重 → 品牌识别 → 事件聚合 → 新闻价值评分 + 热度 + 选题价值评分
          ↓
/studio 热点发现 → 保存为选题
          ↓
选择文章类型 → 选角度 → 大纲 → 正文 → 标题 → 审核
          ↓
轻量富文本排版 → 复制到微信公众号编辑器 → 手动发布
```

### 2.2 关键概念

| 概念 | 定义 | 示例 | 技术落点 |
|---|---|---|---|
| 行业（Industry） | 内容所属领域，固定 7 类 | AI 大模型、汽车、游戏 | `industry/taxonomy.ts` 的 `CATEGORIES` |
| 品牌（Brand） | 新闻涉及的公司、组织或产品主体 | OpenAI、DeepSeek、小米、Apple、华为、奇瑞、特斯拉 | 新表 `wc_brands`，种子来自 `ENTITIES` |
| 渠道（Channel） | 获取信息的平台或具体账号/主页 | X、微信公众号、品牌官网、微博、GitHub、官方媒体 | 新表 `wc_channels` |
| 信源（Source） | 可执行采集的具体订阅对象 | 一条官网 RSS、一个公众号、一个 GitHub 仓库 | 沿用 `sources` |
| 原始条目（SourceItem） | 从单一信源采集的一篇文章、公告或更新 | 一则 Release、一篇公众号文章 | 沿用 `articles` |
| 热点事件（Event） | 一个独立的新闻事实及其相关后续 | 某款模型正式发布 | 沿用 `stories` + `facts` |
| 主题页（Topic Page） | AIHOT 已有的公司、方向、内容形态聚合页 | OpenAI 主题页 | 沿用 `/topics`、`topics.json` |
| 选题（Pitch） | 对热点提出的编辑角度及创作任务 | 新模型的实际体验是否有明显提升 | 新表 `wc_topics` |
| 文章（Article） | 由选题产生、可编辑的稿件 | 一篇科技资讯或洞察稿 | 新表 `wc_articles` |

**重要关系**：

- 一个品牌可对应多个渠道和信源；一个渠道也可关联多个品牌（如综合科技媒体）。
- 一个事件可涉及多个品牌与原始条目；一个事件可产生多个选题；一个选题可关联一篇或多篇草稿。
- 媒体账号是信息发布者，被报道的品牌是事件主体，二者不能混为一谈。
- **“主题页”与“选题”是两个不同的东西**：主题页是公开的聚合页，选题是私有的创作任务。代码和界面文案里不要混用 `topics` 这个词。

### 2.3 行业分类（固定 7 类）

V1 使用以下 7 个公开类别。当前 AIHOT 的“行业”类别在 V1 中退场，公司经营、融资、政策等事件按其主体所在领域归类；无法归类的资料不进入热点列表，只在后台诊断中可见。

| 行业 | key | 范围 | 优先监控事件 |
|---|---|---|---|
| AI 大模型 | `ai-models` | 模型、推理、多模态、API、开源权重 | 新模型发布、版本更新、价格变化 |
| 汽车 | `auto` | 乘用车、智能驾驶、汽车技术及产业 | 官宣、预售、上市、交付、重大技术发布 |
| 数码硬件 | `hardware` | 手机、PC、芯片、可穿戴、影像、外设 | 新品发布、规格与价格、开售 |
| 软件与互联网 | `software` | 应用、操作系统、工具、互联网产品 | 重要版本、功能更新、开源项目 |
| 具身智能 | `embodied` | 机器人、无人机、智能体与物理世界模型 | 产品发布、技术演示、量产与部署 |
| 电影与剧集 | `film` | 电影、电视剧、动画、流媒体 | 定档、预告、上映、重大行业事件 |
| 游戏 | `game` | 电子游戏、主机、游戏产业 | 官宣、发售、延期、版本更新 |

允许跨行业关联。例如智能驾驶产品可以关联「汽车」与「具身智能」；不为同一事实创建重复事件。

**迁移说明**：

- 新增“汽车”（`auto`）和“游戏”（`game`）两类。
- 现有“电影艺术”改名为“电影与剧集”，范围收窄到电影、剧集、动画和流媒体；游戏从这一类拆出。
- 现有“行业”类别删除；融资、人事、政策、安全等作为标签或事件类型保留，事件按其主体所在领域归类。
- 类别 key 上线后不再改变；`/feed/category/<key>.xml` 等公开出口如果保留，按新 key 输出。
- 分类调整后要用真实样本重新校准 `industry/selection.ts` 的门槛，不能直接沿用 AI 行业的数字。

## 3. 信息架构与导航

### 3.1 产品入口与公开站退场

V1 起：

- `/` 重定向到 `/studio`。未登录时进入管理员登录，登录后回到 `/studio`。
- `/studio` 是产品主界面，拥有自己的桌面侧栏、移动底栏和页面框架，不复用公开站的读者导航。
- 公开阅读页（`/all`、`/hot`、`/story`、`/daily`、`/weekly`、`/monthly`、`/topics` 等）不再出现在导航中，并逐步下线。
- 在公开页正式下线前，它们必须设置 `noindex`，且不能展示 `wc_` 私有数据（选题、稿件、关注、通知）。
- 现有 RSS、API v1、MCP 等机器出口在 V1 暂时保留，作为兼容能力；它们只输出 AIHOT 原有公开内容，不输出工作台私有内容。是否在 P1 一并下线，按实际订阅情况决定。
- 品牌详情复用 `/topics` 的数据与视觉能力，但品牌关注、渠道和事件筛选属于 Studio 私有页面。

公开站退场分三步：

| 阶段 | 状态 |
|---|---|
| V1.0 | `/` → `/studio`；公开页从导航移除并 `noindex`；机器出口保留 |
| V1.1 / P1 | 下线公开阅读页和日报/周报/月报页面；机器出口按需保留或下线 |
| V2 | 完成替代，AIHOT 阅读界面不再是产品的一部分 |

### 3.2 一级导航

1. **热点发现**：跨行业聚合事件、推荐榜、关注更新、事件详情。
2. **选题管理**：待评估、待研究、待写作、写作中、已完成及归档。
3. **我的文章**：资讯/洞察草稿、文章编辑、排版与导出。
4. **关注与信源**：品牌关注、渠道订阅、GitHub 仓库、抓取状态与规则。
5. **设置**：AI 模型、评分偏好、采集与通知配置、文章风格预设。

排版作为文章编辑器的一种工作模式，不单独设置一级导航。行业、品牌与渠道同时作为热点列表的筛选维度。

### 3.3 核心页面

| 路由 | 页面 |
|---|---|
| `/studio` | 热点发现：行业 Tabs、品牌/渠道过滤器、排序、事件卡片、关注更新 |
| `/studio/events/:publicId` | 事件详情：事件摘要、时间线、原始报道、事实证据、评分解释、创建选题 |
| `/studio/brands` | 品牌库：搜索、新建、别名、关注状态 |
| `/studio/brands/:id` | 品牌详情：品牌简介、关联行业、可用渠道、订阅状态、相关事件 |
| `/studio/sources` | 信源管理：新增 URL/账号/仓库、采集策略、健康状态、验证结果 |
| `/studio/sources/new` | 新增信源向导 |
| `/studio/topics` | 选题看板：按状态管理选题卡片 |
| `/studio/topics/:id` | 选题详情：资料、角度、状态、进入写作 |
| `/studio/articles/:id` | 文章编辑：角度/大纲/正文/标题/审核与排版、预览、复制导出 |
| `/studio/alerts` | 站内通知 |
| `/studio/settings` | 写作风格、评分偏好、通知与采集配置 |

## 4. 功能需求

### 4.1 热点发现（P0）

**目标**：将不同渠道的信息统一转化为可评估的事件卡片。

#### 4.1.1 信息展示与筛选

- 按行业展示热点，支持「全部」与单/多行业筛选。
- 支持品牌、渠道、事件类型、来源等级、时间范围、是否已读、是否已选题的筛选。
- 排序包括「最新发现」「最新进展」「热点分」「选题推荐分」「我的关注优先」。
- 事件卡片包括：标题、简要摘要、品牌标签、行业标签、事件类型、首发时间、最近更新时间、主要来源、聚合条目数、新闻价值、热度、选题推荐分、核实状态和选题状态。
- 操作包括：查看详情、收藏、忽略、关注后续、创建选题。
- 默认展示“有编辑价值”的事件（至少一篇精选报道，或至少两个独立来源）；可切换到“全部已采集事件”查看长尾。

#### 4.1.2 事件聚合与状态

- 复用 AIHOT 事件去重与聚合能力；同一事件的官网发布、媒体解读与社区讨论归在同一事件下。
- 记录发布时间（来源声明）与采集时间，避免把「刚采集到」误判为「刚发生」。
- 对不同发展阶段建立独立事件或关联子事件：如汽车预售、正式上市、交付；模型预告、正式发布、API 上线。
- 核实状态：
  - `待核实`：只有媒体或社区报道，没有一手来源；
  - `已确认`：存在官方一手报道；
  - `存在争议`：人工标记争议，或来源之间事实冲突；
  - `已更新`：事件下出现了新的独立事实，作为附加标记显示，不与前三种互斥。
- 禁止将传闻默认表述为官方事实；事件卡片和详情都要显示核实状态。
- 合并后仍可展开原始链接、发布者、发布时间及更新记录。
- 事件被归组并合并时，选题、已读状态和关注状态要迁移到存活事件，不能留下孤儿引用。

#### 4.1.3 热点榜

- 展示按行业和时间范围划分的推荐热点榜。
- 区分「热度」与「选题价值」；不能仅用报道条数代表全网热度。
- 未接入真实平台互动数据时，热度明确标注为**基于已采集信源的估计**。
- 新闻价值沿用 AIHOT 的精选分；选题价值由事件级评分单独给出，两者并列展示，不互相替代。

**验收标准**：同一事件的重复报道可以聚合并保留来源；可按行业、品牌和渠道筛选；事件可一键转入选题池；合并事件后原选题仍可打开。

### 4.2 品牌与关注（P0）

**目标**：让用户按品牌持续获取动态，而不用逐条维护所有 URL。

#### 4.2.1 品牌档案

- 品牌库以 AIHOT 现有 `ENTITIES` 为种子，并补充官网域名（`PUBLISHER_DOMAINS`）、GitHub 组织、X 账号、公众号等渠道信息。
- V1 优先包含 OpenAI、DeepSeek、Apple、小米、华为、特斯拉、奇瑞等；具体清单由使用者确认。
- 品牌字段：规范名称、别名、Logo、关联行业、官方网站、关联渠道、关联信源、关注状态。
- 支持搜索品牌、手动新建品牌、合并别名及修正错误归属。
- 支持一个品牌关联多条官方账号和产品线；同一信源也可关联多个品牌（如综合科技媒体）。
- 品牌详情页参考现有 `/topics` 的公司主题页：同样的品牌标记、关联事件、时间线结构；但操作（关注、筛选、进入选题）属于 Studio。

#### 4.2.2 一键关注

- 点击「关注品牌」后，展示系统发现的候选官网、X、微博、微信公众号、GitHub 组织/仓库等渠道。
- 区分 `已验证官方`、`用户指定`、`待验证`、`暂不可用`，用户可以单独勾选。
- 关注规则：全部更新 / 仅重大事件 / 指定发布事件 / 自定义关键词。
- 支持取消关注、静音、屏蔽关键词、调整通知频率。
- 品牌身份验证优先依据官网互链、平台认证、组织主页等证据；不可仅凭名称匹配自动认定官方身份。
- 取消或暂停单个渠道，不会取消整个品牌的关注。

**验收标准**：关注一个品牌后，可查看其关联渠道和聚合事件；删除单个渠道不会取消整个品牌的关注；改名或合并品牌后，已有选题和关注仍然有效。

### 4.3 渠道与信源（P0）

**目标**：提供统一、可扩展、可诊断的信息采集入口。

#### 4.3.1 支持的渠道

| 渠道 | 订阅对象 | V1 采集方式 | 说明 |
|---|---|---|---|
| 品牌官网 | 新闻中心、博客、更新日志、产品列表 | RSS / 网页列表 | 优先作为一手来源 |
| X（Twitter） | 品牌或人员公开账号 | 保留现有 `x_search`（SocialData） | 频率和访问权限受平台约束 |
| 微信公众号 | 单一公众号 | 保留现有 `mp_account`（极致了/Dajiala） | 按请求计费；显示真实可用性，不承诺即时 |
| 微博 | 品牌/机构认证账号 | RSSHub / JSON 适配器 | V1 不承诺原生；UI 标注“通过适配器接入” |
| GitHub | 组织、仓库、Release | Release 用 GitHub Atom；P1 增加 API | P0 不新增信源类型 |
| 官方媒体/科技媒体 | 新闻站点、媒体 RSS、公开文章列表 | RSS / JSON / 网页列表 | 区分发布者与被报道主体 |
| 自定义 RSS/API | 用户粘贴的 Feed 或 API | RSS / JSON | 支持连通性测试 |
| 自定义网页 | 无订阅源的公开页面 | 网页列表（选择器） | 整页变化检测放 P1 |

#### 4.3.2 GitHub 专项订阅

GitHub 是独立的渠道类型，其组织、用户及仓库可以关联品牌，也支持直接关注技术主题。

| 订阅层级 | 监控事件 | 优先级 | V1 实现 |
|---|---|---|---|
| 组织/用户 | 关联官方仓库、新增重要仓库、公开项目动态 | P1 | 手动关联仓库 |
| 仓库 Releases | 新版本发布、Pre-release、版本说明 | P0 | `releases.atom` 走 RSS |
| 仓库 Tags | 新 Tag 与版本节点 | P1 | GitHub API |
| 默认分支 Commits | 关键提交、代码演进 | P1 | GitHub API，默认关闭通知 |
| Issues / Pull Requests | 重大功能提议、缺陷、合并进展 | P1 | GitHub API，默认关闭通知 |
| GitHub Trending | 趋势项目榜单、项目发现 | P0 | 复用 AIHOT 已有 `FEED_LISTS` |

GitHub 条目的统一展示字段：`owner/repo`、仓库地址、版本或提交标识、标题、变更摘要、发布时间、原始 URL、事件类型及相关品牌。

**GitHub 特别规则**：

- 新 Release 通常比普通 Commit 更适合触发即时提醒；高频 Commit 默认仅进入动态流。
- Release、Tag、Commit 不能简单视作三条独立的产品发布；按版本与时间关系去重和关联。
- 区分官方品牌仓库、第三方项目和个人 Fork；不能因项目名称相似就归为某品牌官方发布。
- 仓库级监控优先覆盖公开仓库；私有仓库需授权，不是 V1 必选能力。
- 使用 GitHub API 时遵守速率限制，支持条件请求、退避重试和任务状态记录。
- 对无管理权限的第三方仓库，主要采用轮询/API/公开 Feed；不假设可以为任意仓库创建 Webhook。

**P0 GitHub 接入流程**：

1. 粘贴 `https://github.com/owner/repo`。
2. 调用 GitHub API 验证仓库公开可访问；可选 `GITHUB_TOKEN` 提高限额。
3. 判断 owner 是否为品牌官方组织：是 → 官方仓库，关联品牌；否 → 第三方仓库，不关联品牌。
4. 创建 RSS 信源，地址为 `https://github.com/owner/repo/releases.atom`，默认 30 分钟。
5. 试抓预览版本号、说明和链接，确认后保存。

#### 4.3.3 信源添加与维护

**新增流程**：粘贴 URL 或搜索账号 → 自动识别平台 → 测试采集能力 → 选择品牌和行业 → 配置抓取与通知 → 保存。

管理字段包括：来源名称、渠道类型、网址/账号 ID、来源等级、关联品牌、启用状态、最近检查时间、最近成功时间、失败次数、采集频率、错误信息。

状态至少支持：`运行正常`、`待验证`、`认证失效`、`频率受限`、`采集失败`、`已停用`。状态从现有 `sources.health`、`last_error`、`fail_count` 派生，不重复造一套采集状态。

公众号/X/微博等接口不可用时，提示原因和可替代方式，不把「已保存订阅」伪装为「正在成功监控」。

**验收标准**：能添加 RSS、官网和 GitHub 仓库 Release 订阅；能在统一页面查看来源健康状态；采集失败可诊断、可重试且不影响其他信源；公众号和 X 的付费状态可见。

### 4.4 AI 选题（P0）

**目标**：判断一个热点是否值得写，并将其转化为可执行的写作任务。

#### 4.4.1 评分策略

- **沿用 AIHOT 已有评分管线**：预筛、两次评分、信源分级和精选阈值继续用于新闻价值判断，优先复用既有结果。
- 在事件层新增「选题推荐分」，与新闻价值和热度分开展示。
- 选题维度：重要性、账号相关度、读者吸引力、新颖性、时效性、资料完整性。
- 权重可配置，默认权重需用真实样本校准；代码按权重计算总分，模型只给各维度和理由。
- 输出 0–100 分的选题推荐分，并解释主要加分/扣分原因；来源不足时标注低置信度。
- 输出一句话价值判断、推荐栏目（资讯/洞察）、候选报道角度和资料缺口。
- 同一事件多次抓取仅在新证据或重要进展出现时触发重评，避免不必要的模型成本。
- 评分只覆盖候选事件：至少一篇精选报道，或至少两个独立来源；每轮有数量上限。

#### 4.4.2 选题建议与转化

- 允许手动覆盖 AI 结论（推荐/忽略/稍后/已报道），并保留反馈用于后续偏好调优。
- 点击「创建选题」后，保留事件 ID、全部相关来源、生成理由和用户备注。
- 同一事件可以创建多个角度不同的选题；新建时提示已有同事件选题，避免无意识重复。
- 选题的来源快照在创建时固定，之后事件新增报道不会自动改写已有选题，但可以在选题详情里手动刷新。

#### 4.4.3 选题状态

```text
待评估 → 待研究 → 待写作 → 写作中 → 已完成
   └────────┴────────┴────────┴──→ 已忽略
                                  └→ 归档
```

**验收标准**：热点卡片显示分数及可追溯的推荐依据；一键入池时保留来源，能在选题池中调整状态并进入写作；同一事件重复创建有明确提示。

### 4.5 AI 文章写作（P0）

**目标**：以热点证据为基础，完成资讯和洞察两类文章的结构化生成与修订。

#### 4.5.1 文章类型

| 类型 | 预期输出 | 生成重点 |
|---|---|---|
| 资讯 | 新闻快讯、产品发布速报、简讯合集中的单条内容 | 最新事实、关键变化、数据、时间和官方来源 |
| 洞察 | 科普解读、技术与产品分析、行业趋势文章 | 明确问题、分析框架、证据、不同观点与结论 |

「体验」类文章保留为 P1，因为实际体验需用户提供测试过程、设备和结果，不能由 AI 凭空生成。

#### 4.5.2 两种写作模式

- **快速写作**：选择栏目与目标篇幅 → 自动推荐角度、大纲、正文和标题 → 生成可编辑初稿。
- **分步写作**：选择角度 → 确认大纲 → 分段写作 → 生成/修改标题 → 事实审核 → 定稿。
- 两种模式共享相同的文章数据结构，允许快速模式切换到分步精修。

#### 4.5.3 分步需求

1. **角度**：AI 给出若干切入角度与理由，支持手动填写、重生成。
2. **大纲**：根据栏目生成章节结构，支持拖动排序、增删小节和改写要点。
3. **正文**：支持整篇生成与按章节生成；段落级重写、扩写、精简、调整语气。
4. **标题**：生成直述型、问题型、观点型候选标题；人工编辑最终标题。
5. **审核**：列出关键事实、数字、日期、来源，标记未核实或可能夸大的表述。

#### 4.5.4 写作规则和编辑器

- 文章继承事件全部来源，并允许手动添加资料链接或文字备注。
- AI 只使用证据包中的可追溯内容，不能编造采访、测试结果、报价、发布时间或引言。
- 区分「官方明确」「媒体报道」「尚未证实」「作者判断」，不将推测表述为事实。
- 支持可复用的风格预设：栏目、目标读者、字数、语气、标题偏好及禁止表达方式。
- AI 生成后正文必须可手动编辑；保留自动保存、历史版本及恢复。
- 参考资料和事实引用在编辑界面可见；导出时用户可决定是否保留来源列表。
- 正文编辑器使用 TipTap，内容以受限文档 JSON 存储；P1 增加 Markdown 源码模式。

**验收标准**：从选题进入后可生成资讯/洞察草稿；角度、大纲、正文、标题均可修改；编辑操作不会丢失来源关联；可在文章内进入排版模式。

### 4.6 轻量排版（P0）

**目标**：在 WeChatHot 内完成微信公众号文章常见基础样式，不追求复杂图文设计。

#### 4.6.1 排版能力

| 功能 | V1 内容 |
|---|---|
| 字体 | 正文和标题的字体预设，优先选兼容系统与微信编辑器的字体 |
| 字号 | 正文、标题、二级标题等层级字号设置 |
| 行间距 | 统一行高与基础段落行距 |
| 字重 | 加粗/取消加粗 |
| 段落 | 标题层级、段前段后间距、基础对齐 |
| 图片 | 仅提供基础插入、替换、删除与宽度适配 |
| 预览 | 文章编辑视图及 375px 移动端阅读宽度预览 |
| 导出 | 复制带样式富文本；支持纯文本/Markdown 作为备用输出 |

#### 4.6.2 排版交互

- 文章编辑器内提供「内容」与「排版」视图，切换时共用同一份文档数据，不复制文档。
- 支持一键应用排版预设，之后可逐项修改字号、字体和行距。
- 粘贴到公众号后台时优先保留常用基础 HTML/CSS 样式；导出前对富文本进行清理和兼容性处理。
- 对微信不支持或可能丢失的字体、CSS、图片等提供限制说明。
- 图片 V1 不实现 AI 生图、素材库、智能配图、图文环绕及复杂设计模板。
- 图片上传支持 PNG/JPG/WebP，大小上限 5MB，按内容 hash 命名存储。
- 复制图片到公众号后台可能不会自动上传，界面要提示用户手动上传。

#### 4.6.3 微信兼容性规则

- 只输出 `section`、`p`、`h2`、`h3`、`strong`、`img` 等基础标签。
- 字体、字号、行高、段距、颜色、对齐全部写成 inline style。
- 不使用 `class`、`flex`、`grid`、外部字体、复杂选择器和脚本。
- 图片设置 `max-width:100%;height:auto`。
- 导出前用 `sanitize-html` 清理。

**验收标准**：用户能够修改字号、字体、行距、加粗和基础段落样式；复制富文本后在公众号编辑器中保持主要文字层级和段落结构（以真实粘贴测试为准）。

### 4.7 通知与设置（P0 基础 / P1 扩展）

- **P0 站内通知**：新事件提醒、关注品牌更新、采集错误提示、手动已读与静音。
- **P1 外部通知**：飞书/邮件/Web Push、立即/定时摘要两级推送、自定义重要性阈值。
- 按品牌、渠道、事件类型组合设置通知规则；GitHub 普通 Commit 默认不触发高优先级通知。
- 同一事件多条来源更新默认合并通知；重大版本升级或正式发布可再次提醒。
- 显示事件触发时间、通知发送状态及去重原因。
- **P1 发布日历**：按计划发布日查看选题和稿件，不进入 V1 核心闭环。
- 设置页包含：AI 模型、评分权重、采集频率、通知规则、文章风格预设。

**验收标准**：关注品牌后出现站内提醒；同一事件的多条更新只产生一条通知；采集失败有可见提醒；通知可以单条/全部已读和静音。

## 5. 典型用户流程

### 流程 A：关注品牌并发现新品

1. 用户在「关注与信源」搜索 Apple，选择关注。
2. 系统列出已验证/待验证的官网、社交账号与 GitHub 相关信源，用户勾选。
3. 采集任务定时检查新内容，形成原始条目并识别品牌。
4. 多来源报道汇总成事件，经过 AIHOT 评分后进入相应行业热点列表。
5. 若达到关注提醒条件，站内提示；用户打开事件详情并保存为选题。

### 流程 B：订阅 GitHub 发布

1. 用户粘贴仓库链接，例如 `https://github.com/owner/repository`。
2. 系统识别 GitHub 仓库并验证公开访问状态。
3. 默认订阅 Releases；可选 Tags、Commits、Issues/PR（P1）。
4. 发布新 Release 后，系统采集版本号、说明与原始链接，识别与已收录事件的关系。
5. 根据重要程度进入「软件与互联网」或相关领域榜单，满足阈值后提示用户。

### 流程 C：热点转文章

1. 用户从热点列表打开事件，检查新闻价值、热度、选题分、原始证据和相关品牌。
2. 选择「创建选题」，确认栏目（资讯或洞察）。
3. 选择快速写作或分步写作，修改角度与大纲。
4. 生成正文，人工校对事实、数字、来源及措辞。
5. 在排版视图应用样式预设，调整字体、字号、行距并插入必要图片。
6. 复制富文本至微信公众号后台；用户自行审核与发布。

### 流程 D：公开站退场后的日常使用

1. 打开站点，`/` 自动进入 `/studio`。
2. 未登录时先登录管理员账号，登录后回到工作台。
3. 在工作台查看通知、关注更新和热点列表。
4. 不再经过 AIHOT 的公开资讯首页、日报页或主题目录页。

## 6. 数据结构

保留 AIHOT 原有数据模型，在其上增加工作台私有表。**不复用 `topics` 和 `articles` 这两个已经被 AIHOT 占用的表名**。

### 6.1 实体映射

| PRD 实体 | 落地表 | 说明 |

| `brands` | `wc_brands` | 种子来自 `ENTITIES`，可手动新增 |
| `channels` | `wc_channels` | 渠道是平台账号/主页，不等于信源 |

| `sources` | `sources` | 沿用 AIHOT |
| `source_items` | `articles` | 沿用 AIHOT，不新建 `source_items` |
| `events` | `stories` + `facts` | 沿用 AIHOT |

| `follows` | `wc_follows` | 单用户，无 `user_id` |
| 事件状态 | `wc_event_states` | 已读、收藏、忽略、关注后续、人工决策 |
| `topics` | `wc_topics` | 选题，不是主题页 |
| `articles` | `wc_articles` | 稿件，不是原始条目 |
| `article_versions` | `wc_article_versions` | 稿件历史版本 |
| 排版预设 | `wc_style_presets` | 内置 + 自定义 |
| `alerts` | `wc_alerts` | 站内通知 |

- `created_at`

#### `wc_alerts`

- `story_id`
- `kind`：`new_event` / `follow_update` / `source_error`
- `rule_id`
- `dedupe_key`
- `status`：`unread` / `read` / `muted`
- `reason`：触发或去重原因
- `created_at`、`sent_at`

### 6.3 数据规则

- **单用户**：所有 `wc_` 表不加 `user_id`；管理员会话就是唯一用户。
- **事件合并**：`wc_topics`、`wc_event_states`、`wc_event_brands` 以存活 `story_id` 为准；投影任务跟随 `stories.merged_into` 迁移引用。
- **公开范围**：`wc_` 表不进入 `publication/`，不进入 RSS、API v1、MCP、站点地图和分享图。
- **来源可追溯**：选题和稿件保存来源快照，事件后续更新不自动改写历史稿件。
- **删除**：删除选题不删除事件；删除稿件不删除选题；删除品牌不删除事件，只移除关注和渠道关联。
- **迁移**：工作台表放在 `modules/wechathot/migrations/`，按完整文件名排序；从 `0100` 起编号，每个文件一条可在线执行的语句，索引单独文件并使用 `CONCURRENTLY IF NOT EXISTS`。

## 7. 技术实施方案

### 7.1 总体架构

```text
AIHOT 引擎（采集、分析、归组、热度、publication）
        │
        ├── 现有公开读取层（V1 暂时保留，逐步下线）
        │
        └── modules/wechathot
              ├── wc_ 事件投影（只给工作台读）
              ├── /studio 私有页面
              ├── /api/studio/*（管理员会话 + CSRF）
              ├── worker：投影、选题评分、写作、通知
              ├── 自己的提示词、排版预设、迁移、测试
              └── 复用 sources / analyses / stories / facts / hot
```

实现原则：

- **模块化**：产品逻辑全部放 `modules/wechathot/`，框架不导入模块，只读 `site/modules/` 的三份清单。
- **私有**：Studio 页面和接口只允许管理员会话；`no-store`、`noindex`。
- **不调模型的地方不调**：事件投影、筛选、排序、通知匹配用 SQL 和规则；只有选题评分、写作、审核调模型。
- **付费可控**：所有模型调用走 `chatJson`，有回执、预算熔断和模型切换；写作由用户触发。
- **公开出口不混入私有数据**：`wc_` 内容不进入 `publication/`。

### 7.2 复用的 AIHOT 能力

| 能力 | 复用方式 |
|---|---|
| 采集与调度 | 现有 RSS、网页列表、JSON、X、公众号、外部推送；GitHub Release 用 Atom 走 RSS |
| 信源健康 | 读 `sources.health`、`fail_count`、`last_error`、`last_ok_at`、`fetch_runs` |
| 预筛与新闻价值 | 现有 `editorial/analyze.ts`、两次评分、`industry/selection.ts` |
| 事件与事实 | 现有 `stories`、`facts`、`fact_articles`、`story_links` |
| 事件详情 | `publication/stories.ts` 的 `loadStoryDetail`，工作台只读并加私有操作 |
| 热度 | 现有 `events/hot.ts` 和 `hot_rankings` |
| 归组与合并 | 现有 `events/group.ts`、`merge.ts`、`corrections.ts` |
| 主题页 | 现有 `/topics`、`topics.json`、`ENTITIES`、品牌标记组件，用于品牌详情参考 |
| 后台信源 | `admin/sources.ts` 的 `createSource`、`previewSource`、`fetchNow`、`sourceDetail` |
| 付费回执 | `providers/receipts.ts` |
| 模型切换 | 模块 `models` 插口 + `site/models.ts` |
| 管理员会话 | `admin/auth.ts` 的 `sessionPrincipal`、CSRF、审计 |

### 7.3 事件投影

工作台不直接对 `stories` 做复杂多表筛选，而是维护 `wc_event_meta` 读模型：

- 每 5 分钟扫描最近 30 天有更新的存活事件。
- 聚合分类、品牌、渠道、来源等级、报道数、首发/最近时间、热度、代表报道的摘要与主要来源、新闻价值。
- 从 `analyses.subjects` 和 `facts.subject` 用 `entityIdentity()` 映射品牌。
- 按代表报道标签映射事件类型，不额外调模型。
- 按一手来源判断核实状态；新事实标记“已更新”。
- 合并事件时迁移选题、状态和关注引用。
- 投影失败不影响采集和公开链路，只影响工作台显示。

### 7.4 选题评分

- 独立模型步骤 `editorialScore`，可在 `site/models.ts` 和后台模型页配置。
- 输入：事件综述、facts、最近报道标题/摘要/来源/分级/时间、热度、账号定位。
- 输出：六维分数、加权总分、一句话价值判断、推荐栏目、候选角度、资料缺口、置信度。
- 代码按权重计算总分，权重放模块配置；模型只负责维度和理由。
- 只在候选事件、指纹变化、无人工覆盖时评分；每轮限量。
- 人工决策与模型结论分开存储。

### 7.5 写作管线

- 模块队列 `wechathot.write`，步骤：`angle` / `outline` / `body` / `title` / `review`。
- 快速写作一次串起全部步骤；分步写作由用户逐步触发。
- 每个步骤用 `chatJson` + zod schema，`subject` 带 `article:<id>:<step>:<revision>`，重试复用回执。
- 证据包：事件综述、facts、最近 N 条报道的标题/摘要/来源/时间/链接、用户补充资料。
- 生成后写回 `wc_articles`，并建立版本；审核结果单独存 `review`。
- 正文编辑器使用 TipTap，文档 JSON 为唯一内容源；排版设置单独存 `format`。

### 7.6 排版与复制

- 内容视图与排版视图共用文档数据。
- 排版预设存 `wc_style_presets`，应用后逐项可改。
- 导出时序列化为 inline style 的微信兼容 HTML，同时提供纯文本/Markdown。
- 复制使用 `navigator.clipboard.write`，失败时回退到隐藏 `contentEditable` + `execCommand("copy")`。
- 图片上传到 `AIHOT_DATA_DIR/uploads/`，按内容 hash 命名，模块路由提供预览。
- 真实公众号后台粘贴测试是 P0-C 发布门槛。

### 7.7 鉴权与安全

- Studio 复用管理员登录，不新建账号体系。
- 模块 API 用 `sessionPrincipal` 校验会话；非 GET 校验 `x-csrf-token`。
- 所有 Studio 响应 `Cache-Control: no-store`，页面 `noindex, nofollow`。
- 写操作记录审计。
- 上传校验类型、大小和内容；URL 导入遵守现有抓取安全限制，防止 SSRF。
- 提示词把信源内容视为数据，不执行其中的指令。

### 7.8 部署与运行

- 继续使用现有 Docker Compose / Node.js 24 / PostgreSQL。
- 模块在 `site/modules/` 注册，`site/package.json` 加依赖，`Dockerfile` 加 `COPY`。
- 新增迁移随 `npm run db:migrate` 自动执行。
- 新增可选环境变量：`GITHUB_TOKEN`（P1 GitHub API）；P0 不需要。
- 公众号和 X 继续使用现有 `DAJIALA_KEY`、SocialData 配置和预算。
- 不新增外部服务依赖；P1 如需微博原生连接器，再单独部署适配器。

### 7.9 公开站退场的技术处理

- V1：模块加 `redirects`，`/` → `/studio`（302）。
- 公开页从导航移除并设置 `noindex`；保留 URL 直到 P1 下线。
- P1：按实际使用情况删除公开阅读路由、日报/周报/月报页面和主题目录页；保留数据表和 `publication/`，避免破坏引擎内部依赖。
- 机器出口（RSS、API、MCP）在 V1 保留但不再宣传；P1 决定是否下线。任何阶段都不得输出 `wc_` 数据。

## 9. MVP 验收与指标

### 9.1 核心验收清单

- [ ] 热点能按 7 类行业、品牌、渠道筛选，重复报道能够聚合。
- [ ] 可以新增 RSS、官网以及公开 GitHub 仓库的 Release 订阅。
- [ ] 信源出现失败、限流、认证失效时有可见状态与错误原因。
- [ ] 可以关注品牌，筛选其相关事件，并独立配置渠道。
- [ ] 热点具备新闻价值、热度、选题推荐分、依据说明和原始出处，可保存为选题。
- [ ] 一个事件可形成资讯或洞察草稿；角度、大纲、正文与标题可编辑。
- [ ] 文章支持保存与恢复，来源和事实依据不会在写作过程中丢失。
- [ ] 支持字号、字体、行距、加粗、基础段落、图片与复制富文本。
- [ ] 真实微信公众号后台粘贴测试能够保留主要文字结构和基础排版。
- [ ] `/` 进入 `/studio`；未登录先登录；公开页不再作为产品主界面。
- [ ] 合并事件后，原有选题、已读状态和关注仍然有效。
- [ ] 同一事件的多条来源更新合并为一条站内通知。

### 9.2 上线后观测指标

- **信源成功率**：按渠道记录有效抓取、失效、延迟、重复率。
- **重要事件漏报率**：按人工维护的基准事件集抽查。
- **重复事件率**：相同事实被拆成多个未关联事件的比例。
- **选题采纳率**：用户将推荐事件保存为选题的比例。
- **草稿完成率**：进入写作后完成审核和排版的比例。
- **生成成本**：每篇文章及每 100 条采集信息的模型调用开销。
- **人工改写率**：AI 初稿被用户大改的比例，用于评估写作质量。

首版不设未经测试的硬性数值目标，先收集基线数据，再制定阈值。

## 10. 风险与待决策项

| 风险或决策 | 处理方式 |
|---|---|
| 公众号缺少通用稳定的官方第三方抓取能力 | 继续使用现有极致了适配器；展示真实可用性；准备手动导入兜底 |
| X、微博接口限制或收费 | 保留现有 X 能力；微博先走 RSSHub/JSON 适配器；不承诺全量实时 |
| GitHub 高频 Commit 带来噪声 | 默认 Release 优先；Commit/PR 放 P1 且默认关闭通知 |
| GitHub API 限流 | P0 用 Atom 不耗配额；P1 条件请求、退避、可选 token |
| AIHOT 上游改动与 Fork 定制冲突 | 产品逻辑全部放模块；框架只读清单；P1 新信源类型才改框架 |
| AI 误判热点、编造事实、重复写作 | 来源校验、低置信度提示、审核清单、已报道记录、证据包 |
| 微信编辑器粘贴时样式丢失 | 使用兼容 HTML/CSS 子集；真实粘贴验证；提供纯文本/Markdown 兜底 |
| 过量采集与模型调用 | 按信源等级、更新频率、评分指纹和用户触发控制成本 |
| 第三方内容的版权与平台规则 | 只存储必要元数据和允许使用的摘要/内容；保留原始链接和出处 |
| 公开站下线影响现有读者 | 分阶段退场；V1 保留 URL 和机器出口；P1 按实际使用决定 |
| 7 类迁移导致分类和测试大量变化 | 单独工作流；用真实样本重新校准；逐项替换测试样例 |

**仍需确认的产品选择**：

- 首批重点关注品牌清单，以及每个品牌的官网、X、公众号、GitHub 组织。
- 公众号采集服务的预算与可用范围。
- X 采集的预算与账号范围。
- 是否在 P1 下线 RSS/API/MCP，还是保留给外部订阅者。
- 站点名称、Logo、域名、备案信息和使用条款内容。
- 写作默认模型和单篇成本上限。

这些决策不妨碍按本 PRD 启动 M0 和 P0-A。

## 11. 最终产品边界

WeChatHot V1 应完整实现：

> 从品牌/渠道订阅收集信息，经 AIHOT 识别和筛选热点；在 `/studio` 中评估选题价值，保存为选题；由 AI 辅助完成资讯或洞察写作；使用轻量编辑器排版，复制到微信公众号后台，由用户手动发布。

V1 不包含：

- 公众号自动发布；
- 自动生成真实产品体验；
- 复杂图片编辑、素材库、AI 配图；
- 多用户协作、团队权限；
- 无人审核的自动批量发文；
- 公开资讯阅读器作为主产品。

产品的首要交付价值是：**更及时发现重要信息、更少重复阅读、更快形成可核查且可发布的文章。**
